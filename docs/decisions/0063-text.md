# 0063. `char`'s questions are Unicode regular expressions; `parse` is a `Result` of Rust's message

Status: Accepted. Extends [0034](0034-strings-and-chars.md) and [0060](0060-debug.md).

## Context

Programs that read text ask what a `char` is (`c.is_alphabetic()`,
`c.to_digit(10)`), turn words into numbers (`s.parse::<u32>()`), split
input (`split_whitespace`, `lines`), cast between `char` and numbers, and
take part of a slice (`&v[1..3]`). All of these were errors.

A `char` is a one-character string (ADR 0034), so JS has no methods for
it, and JS's own tests don't match Rust's: `\s` also matches U+FEFF, which
Rust's `is_whitespace` doesn't, and `parseInt("4x")` is 4, which Rust
rejects.

## Decision

**A `char` question is a regular expression of the Unicode property Rust
uses,** and a JS regular expression with `u` names the same properties:

| Rust | JS |
|---|---|
| `c.is_whitespace()`, `is_alphabetic()`, `is_numeric()` | `/^\p{White_Space}$/u.test(c)`, `\p{Alphabetic}`, `\p{N}` |
| `c.is_uppercase()`, `is_lowercase()`, `is_control()` | `\p{Uppercase}`, `\p{Lowercase}`, `\p{Cc}` |
| `c.is_ascii_digit()` and the other `is_ascii_*` | `/^[0-9]$/.test(c)`, … |
| `c.to_ascii_uppercase()` | `c.replace(/[a-z]/, (letter) => letter.toUpperCase())` |
| `c.to_digit(16)`, `c.is_digit(8)` | `$toDigit(c, 16)`, `$toDigit(c, 8) !== undefined` |
| `c as u32`, `b as char` | `c.codePointAt(0)`, `String.fromCharCode(b)` |
| `s.split_whitespace()` | `s.split(/\p{White_Space}+/u).filter((word) => word !== "")` |
| `s.lines()` | `$lines(s)`: `\n` or `\r\n`, without a last empty line |
| `s.split(\|c\| ..)`, `s.contains(\|c\| ..)` | `$splitBy(s, (c) => ..)`, `Array.from(s).some((c) => ..)` |
| `s += t` | `s += t` |
| `s.parse::<u32>()`, `::<f64>()` | `$parseInt(s, 0, 4294967295)`, `$parseF64(s)` |
| `s.parse::<bool>()`, `::<char>()` | `$parseBool(s)`, `$parseChar(s)` |
| `&v[1..3]`, `&v[2..]`, `&v[..1]` | `$slice(v, 1, 3)`, `$slice(v, 2)`, `$slice(v, 0, 1)` |

- **`parse` is a `Result` whose `Err` is Rust's message,** such as
  `"invalid digit found in string"`, since a parse error's `to_string()`
  is all a program can get from it here. So `map_err(|e| e.to_string())`
  changes nothing, and of a `Result` just made it's left out:
  `const n = $parseInt(s, 0, 4294967295);`. `$parseInt` takes the
  type's range, so `"200"` is too large for an `i8`, and it rejects what
  Rust rejects: `" 1"`, `"1.5"`, `"-1"` for an unsigned type.
- **A slice by a range is a copy,** which a shared slice can be: nothing
  changes `v` while it's borrowed. Out of range, it panics with Rust's
  message. `&mut v[a..b]` is still an error.
- **`{:?}` of a string escapes what Rust escapes,** with `$debugStr`, in
  place of `JSON.stringify`: `\u{1b}`, not `\u001b`, and the invisible
  characters JSON leaves as they are (`\u{feff}`, `\u{200b}`, `\u{a0}`).
- **Also here:**
  - byte literals: `b'a'` is `97`;
  - `?` from a `&str` error to a `String` one returns the `Err` as it
    is: both are the same JS string;
  - std's own `into()` and `From` between numbers and to `String` are the
    value itself.
- **Still errors:** `parse` to other types, slicing by a range held in a
  variable, `{:?}` of a parse error, and what counts a string's UTF-8
  bytes (ADR 0034): `&s[a..b]`, and the offsets `find`, `rfind` and
  `char_indices` give.

## Why

- **It's Rust's answer, character for character.** Differential tests
  check each question on ASCII and non-ASCII `char`s (`'\u{3000}'`, `'٣'`,
  `'Ⅻ'`, `'\u{feff}'`), and `parse` on the edge cases: empty, signs,
  overflow, `inf`, `NaN`, leading spaces.
- **It's the JS a person would write.** A regular expression is how JS
  asks what a character is, and `\p{…}` is exact where a hand-written range
  isn't.

## Alternatives

- **JS's `\s`, `parseInt` and `Number`:** shorter, but each disagrees with
  Rust somewhere (`\s` and U+FEFF; `parseInt("4x")` is 4; `Number("")` is
  0).
- **A parse error as an object with a `kind`,** as Rust has it. It would
  allow `{:?}` and matching on the kind, but programs show a parse error's
  message and rarely do anything else with it.
- **A slice as a view** (`subarray` isn't there for arrays; a proxy would
  be one). It would allow `&mut v[a..b]`, but every read would go through
  it.
